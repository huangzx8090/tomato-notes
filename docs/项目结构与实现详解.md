## 1. 先认识这个项目

**番茄小记**是一个"番茄钟 + 待办 + 便签 + 时间统计"的桌面工具。

它解决的核心问题不是"倒计时 25 分钟"——手机上一堆 App 都能做。它想做的是：

> 你专注完之后，能自动留下"这段时间到底干了什么"的证据，而不是让你凭记忆写复盘。

所以它的功能链路是：

```
开始专注（可选填目标）
   ↓
计时期间悄悄记录：前台是哪个 App、Chrome 开着什么页面、便签改了什么、完成了哪些待办
   ↓
一轮结束 → 本机生成"进展卡"（不需要联网、不需要 API Key）
   ↓
可选：让 AI 把零散材料整理成"做了什么 / 取得什么成果 / 待继续 / 待确认"
   ↓
按天、按周汇总成热力图和历史搜索
```

**关键设计原则**（写在需求书和 README 里，也体现在代码里）：

- **目标是计划，App 时长是投入，都不等于完成。** 只有你勾选的待办、你写的描述、你传的图片才算"成果"。
- **默认不联网。** 所有 AI 功能默认关闭，开启前会说明"要发送什么给谁"。
- **数据在你自己的电脑上。** 没有账号、没有云同步、没有自动更新器。

## 2. 整体架构：一个仓库，两个原生客户端

这是理解这个项目最重要的一件事：

```
tomato-notes/                 ← 一个 Git 仓库
├── apps/macos/               ← 完整的 macOS 应用（Swift 写的）
└── apps/windows/             ← 完整的 Windows 应用（C# 写的）
```

**它不是"一套代码编译到两个平台"**，而是两套独立代码：

- macOS 用 **Swift + SwiftUI/AppKit**
- Windows 用 **C# + WPF**

为什么这么做？因为两个平台的系统能力差别太大。比如 macOS 上"读取 Chrome 当前标签页"用的是 AppleScript，"关闭标签"用的是 Apple Events 权限；Windows 上根本没有对应机制。强行统一会写出一堆 `if (是Mac) ... else ...`，最后两边都难维护。

**它们共享什么？**

| 共享的东西 | 位置 | 怎么保证一致 |
|---|---|---|
| 数据格式（JSON 结构） | `Compatibility/data-contract-v4.json` | 双端都读这份样例做回归测试 |
| 产品版本号 | 根目录 `VERSION` | `Scripts/check-versions.py` 校验三处配置一致 |
| 发布流程 | `.github/workflows/` | 同一个 tag 触发双端打包，汇总到一个 Release |
| 分支与协作规则 | `AGENTS.md`、`CONTRIBUTING.md` | 人工 + CI 检查 |

**它们不共享什么？**

- UI 代码、业务逻辑实现、系统调用、测试用例——各自独立。
- 密钥存储：macOS 用钥匙串（Keychain），Windows 用 DPAPI，**不能互相迁移**。

## 3. 技术栈逐项解释

### 3.1 macOS 端

| 技术 | 是什么 | 在这个项目里干什么 |
|---|---|---|
| **Swift** | 苹果官方的编程语言 | 写全部 macOS 代码 |
| **Swift Package Manager (SwiftPM)** | Swift 的官方依赖与构建工具，类似 Java 的 Maven | 管理工程结构、编译、跑测试。见 `apps/macos/Package.swift` |
| **SwiftUI** | 苹果的声明式 UI 框架（类似 React 的思路：描述"界面应该长什么样"） | 写主面板、设置页、历史搜索窗口等 |
| **AppKit** | 苹果更底层的传统 UI 框架 | 状态栏图标（`NSStatusItem`）、弹出面板（`NSPopover`）、窗口管理 |
| **Swift Testing** | 苹果新的测试框架，写法是 `@Test func xxx()` | 写单元测试。项目用 `--disable-xctest` 明确只跑这一套 |
| **Carbon** | 一个很老的 macOS 框架 | 只为了用它的全局快捷键注册 API（`RegisterEventHotKey`） |
| **Security.framework** | 系统安全框架 | 读写钥匙串，保存 AI API Key |
| **UserNotifications** | 系统通知框架 | 番茄结束、休息开始时的提醒 |
| **IOKit** | 硬件/电源相关框架 | 判断是否合盖、是否睡眠 |
| **ScreenCaptureKit** | 屏幕截图框架 | 守护功能里截取 Chrome 窗口给 AI 看 |
| **AppleScript / Apple Events** | 苹果的脚本自动化机制 | 读取 Chrome 标签页标题和网址、关闭标签 |

**为什么 UI 是 SwiftUI + AppKit 混用？**

因为 SwiftUI 擅长画界面，但不擅长做"菜单栏常驻应用"。这类应用需要 `NSStatusItem`（屏幕右上角的小图标）和 `NSPopover`（点图标弹出的浮层），这些只有 AppKit 提供。所以是：

```
AppKit 管"壳"（状态栏图标、弹出容器、窗口）
SwiftUI 管"内容"（浮层里画什么）
```

代码里通过 `NSHostingController` 把 SwiftUI 视图塞进 AppKit 的容器。

### 3.2 Windows 端

| 技术 | 是什么 | 在这个项目里干什么 |
|---|---|---|
| **C#** | 微软的编程语言 | 写全部 Windows 代码 |
| **.NET 8** | 微软的运行时和开发平台 | 程序运行的基础 |
| **WPF** | Windows 的桌面 UI 框架，用 XAML 描述界面 | 主窗口、设置窗口、便签窗口 |
| **WinForms** | 更老的 Windows UI 框架 | **只**用来做托盘图标（`NotifyIcon`），因为 WPF 没有托盘控件 |
| **System.Text.Json** | .NET 自带的 JSON 库 | 读写数据文件 |
| **DPAPI** | Windows 的数据保护 API，用当前用户身份加密 | 保存 AI API Key（替代 macOS 钥匙串） |
| **P/Invoke** | C# 调用 Windows 原生 API 的机制 | 注册全局快捷键（`RegisterHotKey`）、读取前台窗口 |
| **Inno Setup 6** | 一个免费的 Windows 安装包制作工具 | 把程序打成 `setup.exe` |

**"自包含发布"是什么意思？**

普通的 .NET 程序要求用户电脑上先装 .NET 运行时。这个项目用的是 `--self-contained true`，也就是把运行时**一起打进安装包**，用户不需要额外装任何东西，代价是安装包大一些（几十 MB）。

### 3.3 双端共用的技术概念

| 概念 | 解释 |
|---|---|
| **JSON** | 一种文本格式，用 `{}` 和 `[]` 表示结构化数据。两端的数据文件都是 JSON |
| **OpenAI 兼容接口** | 一种事实标准：`POST /chat/completions` 发消息、拿回复。DeepSeek、Kimi、通义、智谱、OpenRouter 都兼容这套，所以换服务商只需要改地址和 Key |
| **Apple 基准日期** | 苹果的时间表示法：从 **2001-01-01 00:00:00 UTC** 开始算的秒数。双端统一用它，避免时区/格式混乱 |
| **原子写** | 写文件时先写临时文件，再整体替换。这样即使写到一半断电，原文件也不会变成半截垃圾 |
| **ad-hoc 签名** | macOS 的"自己给自己盖章"签名，能证明文件没损坏，但**不能证明是谁做的**。所以首次打开可能被系统拦 |

**`VERSION` 为什么单独一个文件？**

因为版本号要出现在至少 5 个地方（macOS 的 Info.plist、Windows 的 csproj 三个字段、安装器配置）。如果各写各的，迟早不一致。所以：

```
VERSION 写 1.6.3
   ↓
Scripts/check-versions.py 检查其他配置是否都是 1.6.3
   ↓
CI 里跑这个脚本，不一致就直接红
```

### 4.2 `apps/macos/`

**这个分层是项目的核心设计，一定要理解：**

```
┌─────────────────────────────────────┐
│  TomatoNotes（界面层）                │  ← 只有这层能碰 UI
│  AppState / Views / 各种 Window      │

               │ 调用

│  TomatoSystem（系统层）               │  ← 只有这层能碰系统 API
│  ChromeBrowser / AIReviewClient     │
│  HotkeyManager / ImageStore         │
└──────────────┬──────────────────────┘
               │ 调用
┌──────────────▼──────────────────────┐
│  TomatoCore（核心层）                 │  ← 纯数据与算法，可以脱离 macOS 测试
```

**好处**：核心逻辑（比如"跨午夜的专注时间怎么分配"）可以在没有界面的情况下单独测试。`TomatoCoreTests` 里有 19 个测试文件，全部不依赖图形界面。

### 4.4 `Compatibility/`

```text
Compatibility/
├── README.md                    # 契约规则说明
└── data-contract-v4.json        # 一份最小的示例数据，两端都拿它做测试
```

这是**双端兼容的"合同"**。规则：

- 两端都读这份 JSON，解析 → 再写出来 → 检查关键字段没变。
- 不允许"为了让一端测试通过"去改这份样例。
- 要改格式，必须两端一起评审、同时更新解析和迁移逻辑。
- **不认识的字段必须原样保留**，不能因为"我这端用不到"就删掉。

最后这条很重要：macOS 独有的字段（比如 Chrome 守护配置），Windows 读进来不认识，但保存时必须原样写回去，否则 macOS 端的数据就被 Windows 端悄悄破坏了。

## 5. macOS 端是怎么跑起来的

### 5.1 启动流程

入口在 `apps/macos/Sources/TomatoNotes/main.swift`。

```
程序启动
  ↓
创建 NSApplication（macOS 应用的根对象）
  ↓
创建 AppCoordinator 并设为 delegate
  ↓
applicationDidFinishLaunching() 被系统调用
  ↓
start()
  ├── 创建 NSStatusItem         → 屏幕右上角出现小图标
  ├── 创建 AppState             → 读数据、恢复计时状态
  ├── 创建 NSPopover + SwiftUI  → 准备好点击后弹出的面板
  ├── 注册系统通知观察者         → 睡眠、锁屏、屏幕变化、App 切换
  └── 注册全局快捷键             → Command+Option+P 等
  ↓
进入事件循环，等待用户操作
```

**关键点**：这是一个**菜单栏应用**（`LSUIElement = true`），默认不在 Dock 显示图标，也不占任务栏。所有操作从右上角的小图标开始。

`applicationShouldTerminateAfterLastWindowClosed` 返回 `false`（`main.swift:176`），意思是"窗口全关了也别退出"。

### 5.2 AppState：整个应用的"大脑"

`apps/macos/Sources/TomatoNotes/AppState.swift` 有 **1146 行**，是全项目最大的文件。它的职责是：

| 职责 | 说明 |
|---|---|
| 持有数据 | `@Published private(set) var data: AppData` |
| 驱动计时 | `tick()` 每 0.25 秒左右被调用，推进倒计时 |
| 决定何时保存 | 关键动作立刻存，普通推进每 2 秒存一次 |
| 协调 AI | 调用 `AIReviewClient`，管理加载状态和错误 |
| 管理系统事件 | 睡眠、锁屏、App 切换、合盖 |
| 通知 UI 刷新 | 通过 `@Published` 属性变化自动刷新 SwiftUI |

**`@Published` 是什么？**

SwiftUI 的"响应式"机制。一个属性标了 `@Published`，它变化时所有用到它的界面会自动重画。你不需要手动写"更新界面"的代码。

**为什么要用单调时钟而不是普通时间？**

代码里用 `ProcessInfo.processInfo.systemUptime`（`AppState.swift:1106`）。这是"开机后经过的秒数"，不受系统时间被修改的影响。如果你手动把电脑时间往前调 1 小时，用普通时间算倒计时会瞬间结束；用单调时钟就不会。

### 5.3 计时引擎

`apps/macos/Sources/TomatoCore/TimerEngine.swift` 只有 202 行，是一个**纯值类型**（`struct`），不持有任何外部状态。

它定义了两组概念：

```swift
enum TimerStage { focus, shortBreak, longBreak }   // 阶段：专注 / 短休 / 长休
enum TimerPhase { idle, running, paused, completed } // 相位：空闲 / 运行 / 暂停 / 完成
```

一次典型的循环：

```
idle --开始--> running --时间到--> completed --手动开始--> 下一个阶段 idle
                  ↑    ↓
                  └ 暂停 ┘
```

**为什么"完成"之后要手动开始下一阶段？** 这是产品决策：不自动跳转，避免你还没准备好就被推进休息。

### 5.4 系统集成层做了什么

| 文件 | 作用 | 关键技术 |
|---|---|---|
| `ChromeBrowser.swift` | 读 Chrome 标签页、关闭标签 | Apple Events（比 AppleScript 字符串更底层、更可控） |
| `AIReviewClient.swift` | 调用 AI 接口 | `URLSession` + OpenAI 兼容协议 |
| `AIProviderCredentials.swift` | 保存/读取 API Key | Keychain（钥匙串） |
| `HotkeyManager.swift` | 全局快捷键 | Carbon `RegisterEventHotKey` |
| `FocusPageCapture.swift` | 截取 Chrome 窗口 | ScreenCaptureKit |
| `WorkImageStore.swift` | 图片压缩与存储 | ImageIO |
| `FocusWhitelistSnapshot.swift` | 记录本轮允许的 App/网页 | 纯逻辑 |

**为什么读 Chrome 用 Apple Events 而不是 AppleScript 字符串拼接？**

AppleScript 是字符串，容易因为标题里有引号、换行而注入失败。Apple Events 是结构化 API，能精确控制"读哪个窗口的第几个标签的哪个属性"，也更容易做"关闭前再次确认页面没变"这种安全操作。

## 6. Windows 端是怎么跑起来的

### 6.1 启动流程

入口在 `apps/windows/TomatoNotes/App.xaml.cs`。

```
WPF 启动
  ↓
App.xaml 里 Startup="Application_Startup" 触发
  ↓
Application_Startup()
  ├── 解析命令行参数（--data-dir / --ui-test / --shutdown）

  ├── 创建 LocalRepository → 读 data.json
  ├── 创建 AppState
  ├── 创建 MainWindow
  ├── 创建 TrayService（托盘图标）
  └── window.ShowFromTray()  → 显示主窗口
  ↓
进入消息循环
```

**这里有个刚修好的坑（v1.6.3）**：`App.xaml` 第一行如果漏了 `Startup="Application_Startup"`，上面整段初始化代码**一行都不会执行**。程序会进入消息循环但什么都不做——没窗口、没托盘、不建数据目录。这就是 v1.6.2 用户遇到的"双击没反应"。

**单实例是怎么做的？**

```csharp
singleInstance = new Mutex(true, $"Local\\TomatoNotes-{token}", out var first);
if (!first) { activateSignal.Set(); return; }   // 已有实例：通知它显示窗口，自己退出
```

`token` 是数据目录路径的哈希。所以：同一个数据目录只能开一个实例；用 `--data-dir` 指定不同目录就能开多个（测试用）。

### 6.2 托盘与"关闭不退出"

- `App.xaml` 设置 `ShutdownMode="OnExplicitShutdown"`：不主动退出就一直活着。
- `MainWindow` 的 `Closing` 事件里 `e.Cancel = true; Hide()`：点 X 只是隐藏。
- `TrayService`（`WindowsServices.cs:46`）创建托盘图标，菜单有"打开/快速待办/新建便签/退出"。
- 真正退出走 `ExitApplication()`，会先 `PrepareForQuit()` 保存数据。

| 功能 | macOS | Windows |

## 7. 数据模型：整个应用的地基

所有数据最终都在一个 `AppData` 对象里，序列化成一个 `data.json`。

### 7.1 顶层结构

```json
{
  "schemaVersion": 4,
  "settings": { ... },
  "timer": { ... },
  "sessions": [ ... ],
  "intervals": [ ... ],
  "usage": [ ... ],
  "todos": [ ... ],
  "notes": [ ... ],
  "workRecords": [ ... ]
}
```

### 7.2 每个实体的含义

| 实体 | 是什么 | 关键字段 |
|---|---|---|
| `settings` | 所有用户设置 | 专注/休息时长、外观、AI 配置、快捷键、守护开关 |
| `timer` | 当前计时状态 | 阶段、相位、目标秒数、剩余秒数、本组已完成轮数 |
| `sessions` | **一轮番茄** | id、开始/结束时间、结束那天、是否完成、本轮目标 |
| `intervals` | **一段真实专注** | 属于哪轮、开始/结束、本地日期、时区、秒数 |
| `usage` | **一段前台 App 停留** | App 名、Bundle ID、开始/结束、秒数、类型 |
| `todos` | 待办事项 | id、文字、创建日、完成时间、完成日、**安排到哪些天** |
| `notes` | 浮动便签 | id、标题、正文、日期、窗口尺寸与位置 |
| `workRecords` | **一轮/一天的成果** | 用户补充的文字、图片、AI 总结 |

### 7.3 为什么 `sessions` 和 `intervals` 要分开？

这是整个数据模型里最精妙的地方。

- **`sessions`（轮次）** 是"你按了一次开始、按了一次结束"这件事。
- **`intervals`（片段）** 是"真正在专注"的时间段。

为什么要拆？因为中间可能暂停、可能跨午夜、可能锁屏。

举例：

```
你 23:50 开始一轮 25 分钟番茄
23:55 暂停了 5 分钟
00:00 继续
00:10 结束

session:  23:50 → 00:10（跨了午夜）
interval1: 23:50 → 23:55，localDay = 今天，300 秒
interval2: 00:00 → 00:10，localDay = 明天，600 秒
```

如果不拆，你没法正确回答"昨天我专注了多久"——因为一轮跨了两天。拆成 interval 后，每天只统计落在自己那天的片段。

**暂停的时间不计入任何 interval**，所以"暂停 5 分钟"不会污染统计。

### 7.4 待办的 `scheduledDays` 为什么是数组？

因为待办可以"手动结转"：昨天没做完的事，你可以安排到今天。这时候它不是复制一条新待办，而是**同一条待办多了一个安排日期**。

```
TodoItem {
  id: "abc",
  text: "写周报",
  localDay: "2026-10-26",        // 最初创建那天
  scheduledDays: ["2026-10-26", "2026-10-27"],  // 安排到过哪些天
  completedAt: ...,
  completedLocalDay: "2026-10-27"  // 实际完成那天
}
```

这样"完成数按实际完成日计算"，同时保留"这项任务本来是哪天的"。

### 7.5 时间为什么用秒数而不是字符串？

双端统一用 **Apple 基准秒数**：从 2001-01-01 00:00:00 UTC 开始算的 `double`。

```json
"startedAt": 0,
"endedAt": 60
```

好处：

- 没有时区歧义（UTC 基准）。
- 没有格式歧义（不用纠结 `2026-10-27` 还是 `2026/10/27`）。
- 双端解析逻辑简单。

坏处：人看不懂。所以调试时要用工具转换。

Windows 端为此专门写了 `AppleDateConverter`（`JsonStorage.cs:7`），在 `DateTimeOffset` 和秒数之间自动转换。

**注意**：日期字段（`localDay`、`endedLocalDay`）仍然用字符串 `"YYYY-MM-DD"`，因为它们是"日历日"概念，不是时间点。

## 8. 数据存在哪、怎么存、怎么不丢

### 8.1 位置

| 平台 | 路径 |
|---|---|
| macOS | `~/Library/Application Support/TomatoNotes/data.json` |
| Windows | `%APPDATA%\TomatoNotes\data.json` |

同目录下还有：

```
data.json              # 主数据
Attachments/           # 成果图片
Backups/               # 备份
```

### 8.2 保存策略

代码在 `LocalRepository.swift:54`：

```swift
try encoder.encode(data).write(to: fileURL, options: .atomic)
```

`.atomic` 的意思是：先写到临时文件，写成功后**整体替换**原文件。这样即使写到一半断电，原文件仍然是完整的旧版本，不会变成半截 JSON。

**什么时候保存？**

- 关键动作（开始、暂停、结束、加待办）→ 立即保存
- 普通计时推进 → 每 2 秒保存一次（`AppState.swift:1087`）

每 2 秒存一次是为了防止崩溃丢太多数据，又不能每 0.25 秒存一次（磁盘 IO 太频繁）。

### 8.3 版本升级与备份

数据格式有版本号 `schemaVersion`，当前是 **4**。

读取时（`LocalRepository.swift:42`）：

```
读 data.json
  ↓
版本号 > 4 ？ → 报错，拒绝读取（防止新版数据被旧版破坏）
  ↓
版本号 < 4 ？ → 先把原始字节备份到 Backups/schema-vN/，再升级
  ↓
返回数据
```

**为什么要先备份原始字节？** 因为升级是不可逆的。如果升级逻辑有 bug，你至少还有原始文件可以回退。

### 8.4 单实例与文件锁

两端都做了"同一个数据目录只能一个进程写"：

- macOS：`RepositoryLock.swift` 用文件锁。
- Windows：`LocalRepository` 持有 `lockStream`。

防止两个进程同时写同一个 JSON 导致数据损坏。

### 8.5 手动备份

设置里有"备份数据"，会复制：

```
data.json
data-xxx.assets/Attachments/*.jpg
```

恢复时两个都要还原，只还原 JSON 会丢图片。

## 9. 双端兼容：一份 JSON 两种语言读

### 9.1 契约测试怎么跑

`Compatibility/data-contract-v4.json` 是一份"最小但覆盖所有字段"的样例。

两端各自有测试：

- macOS：`Tests/TomatoCoreTests/WindowsCompatibilityTests.swift`
- Windows：`TomatoNotes.Tests/Program.cs` 里的"双端共享 v4 资料契约"

测试流程：

```
读样例 JSON
  ↓
解析成各自的数据模型
  ↓
再序列化回 JSON
  ↓
检查：核心字段值没变？Apple 日期转换正确？Unicode 没坏？未知字段还在？
```

### 9.2 "未知字段保留"是怎么实现的

macOS 用了一个协议 `ExtraFieldPreserving`，在解码时把不认识的键存起来，编码时再写回去。

Windows 用 `JsonModel` 基类做类似的事。

**为什么必须这样？**

假设你只用 Windows：

1. Windows 读 `data.json`，里面有个 macOS 专属字段 `focusGuard`。
2. Windows 不认识它。
3. 如果 Windows 直接丢弃，然后保存——macOS 端下次打开就发现守护配置没了。
4. 用户会认为"Windows 版把我的数据搞坏了"。

所以规则是：**不认识 ≠ 可以删**。

### 9.3 密钥为什么不能跨端

- macOS 钥匙串里的 Key，Windows 读不到。
- Windows DPAPI 加密的 Key，macOS 读不到。

这是**故意的安全设计**，不是缺陷。迁移资料时，AI Key 需要在新平台重新填。

## 10. 核心功能实现原理

### 10.1 番茄计时

```
AppState.tick()  每约 0.25 秒被调用
  ↓
用 systemUptime 算真实经过时间
  ↓
TimerEngine 扣减剩余秒数
  ↓
记录当前专注片段（interval）
  ↓
到 0 → 切到 completed → 发通知 → 记录 session
```

**暂停、锁屏、睡眠、合盖**：

- 锁屏 / 睡眠 → 自动暂停（`pauseForSystem`）。
- 合盖但外接显示器 → 默认继续（可在设置关闭）。
- 恢复后**不补计**离线时间。

### 10.2 专注热力图

`TomatoCore/FocusHeatmap.swift`（104 行）。

```
取出所有 FocusInterval
  ↓
按 localDay 分组，累加 seconds
  ↓
映射到色阶（0 / 少 / 中 / 多）
  ↓
画格子
```

关键约束：**只统计真实的番茄专注片段**，暂停、休息、普通活动时长都不算。

今日页显示最近 13 周，独立窗口显示 53 周。

### 10.3 历史搜索

`TomatoCore/HistorySearch.swift`（292 行）。

搜索对象：待办、便签、专注目标、用户成果、AI 总结。

特点：

- 纯本地，不联网。
- 支持类型筛选 + 日期范围。
- 输入防抖（停止输入才搜，不是每按一个键就搜）。
- 分页。
- 点击结果能跳回原记录。

### 10.4 进展卡（不需要 AI）

每轮结束后，本机直接组装：

```
本轮目标
+ 实际专注片段（几点到几点，共多久）
+ 专注期间勾选完成的待办
+ 前台 App 时长
```

注意：**暂停和休息中完成的待办不自动归入上一轮**，避免"我在休息时随手勾了一个，结果算到上一轮成果里"。

### 10.5 AI 回顾

`TomatoSystem/AIReviewClient.swift`（415 行）。

协议：OpenAI 兼容的 `POST /chat/completions`。

支持的服务商（预设）：DeepSeek、OpenAI、智谱、Kimi、通义、硅基流动、OpenRouter，以及自定义地址。

调用链：

```
用户点"让 AI 总结"
  ↓
ReviewContextBuilder 组装材料（文字 + 图片）
  ↓
POST /chat/completions
  ↓
解析 JSON 回复
  ↓
映射成 WorkSummary（做了什么/成果/待继续/待确认）
  ↓
显示 + 保存
```

**图片处理**：每轮最多 6 张，每张原文件 ≤25 MB，导入时统一转成最长边 ≤1600px 的 JPEG。只在真正要总结时才发送。

**错误处理**：错误信息里不能泄露 API Key（有专门的测试 `AIReviewClientTests` 验证）。

### 10.6 AI 自动记录

这是比较新的功能，默认关闭。

```
专注期间（每轮）
  ├── 采样：当前 Chrome 前台页面的标题 + 网站 + 停留时间
  ├── 采样：本轮便签的变更
  └── 采样：完成的待办
  ↓
积累至少约 2 分钟有效材料
  ↓
AI 初步命名主题
  ↓
出现新材料 → 有限次更新（每轮最多 4 次）
  ↓
本轮结束且投入 ≥1 分钟 → 后台整理一次
```

**隐私边界**：

- 不读网页正文。
- 不保存完整 URL 的路径和查询参数。
- 不自动截图。
- 暂停、休息、锁屏时停止采集。

### 10.7 Chrome 专注守护

这是最复杂的系统功能，分三个阶段：

```
阶段 1（纯本机，零 AI）
  检查前台 App / 当前 Chrome 标签是否在白名单
  ↓ 不在白名单且停留超时
阶段 2（纯本机，零 AI）
  轻提醒："你切到了 XX，回到专注吗？"
  ↓ 再等待，仍未返回，且本轮允许 AI 关闭
阶段 3（调用 AI）
  截取当前 Chrome 窗口
  ↓
  AI 判断：这页和本轮目标相关吗？
  ↓ 明确无关，置信度 ≥ 0.9
  重新确认页面没变化（防止 AI 判断期间你切走了）
  ↓
  关闭标签
```

**为什么要三阶段？** 因为 AI 调用慢、花钱、可能出错。绝大多数情况（切到微信、切到 B 站）本机规则就能判断，不需要 AI。AI 只在"页面标题看不出相关性"时才上场。

**为什么关闭前要"重新确认"？** 因为从截图到 AI 回复可能过了几秒，这几秒里你可能已经切到别的页面了。如果不确认，会关错标签。

```
              ├── 已存在且非草稿 → 拒绝
              ├── 创建 draft
              ├── 上传 4 个附件
              ├── 核对服务器实际附件名
              └── 转正 + 标记 latest
```

**`validate-release.sh` 检查什么？**

1. 标签格式是 `vX.Y.Z`，且等于 `VERSION`
2. 必须是 `git tag -a` 创建的**注释标签**（不是轻量标签）
3. 标签指向的提交就是当前检出的提交
4. 这个提交已经在 `origin/main` 的历史里
5. `docs/releases/<tag>.md` 存在且非空

任何一条不满足，发布直接停。

### 12.3 为什么"先 draft 再转正"

因为上传 4 个文件可能中途失败。如果先公开再上传，用户会看到一个"缺文件"的下载页。所以：

```
建草稿（别人看不到）
  ↓
传全部附件
  ↓
回读服务器实际附件名，和期望清单比对
  ↓
一致 → 转正
不一致 → 保持草稿，人工排查
```

## 14. 术语表

| 术语 | 通俗解释 |
|---|---|
| **番茄钟 / Pomodoro** | 一种时间管理法：专注 25 分钟，休息 5 分钟，循环 |
| **阶段（Stage）** | 专注 / 短休 / 长休，三种 |
| **相位（Phase）** | 空闲 / 运行 / 暂停 / 完成，四种 |
| **一轮（Session）** | 你按一次开始到按一次结束 |
| **片段（Interval）** | 一轮里真正在专注的时间段，暂停会切开 |
| **资料库（Repository）** | 存放 `data.json` 的目录 |
| **契约（Contract）** | 双端约定的数据格式，用 `data-contract-v4.json` 固化 |
| **原子写（Atomic Write）** | 先写临时文件再整体替换，防止写坏 |
| **单实例（Single Instance）** | 同一个数据目录只允许一个程序在跑 |
| **自包含（Self-contained）** | 把运行时一起打包，用户不用另装 |
| **ad-hoc 签名** | 自己给自己盖章，能防损坏但不能证明身份 |
| **公证（Notarization）** | 苹果官方审核签名，需要付费开发者账号 |
| **DPAPI** | Windows 的用户级加密 API |
| **Keychain / 钥匙串** | macOS 的密码保险箱 |
| **P/Invoke** | C# 调用 Windows 原生函数的方式 |
| **Apple Events** | 苹果的结构化自动化接口 |
| **单调时钟（Monotonic Clock）** | 只往前走、不受系统时间修改影响的计时器 |
| **schemaVersion** | 数据格式的版本号，当前是 4 |

## 15. 设计取舍与已知限制

### 15.1 有意为之的取舍

| 决策 | 原因 | 代价 |
|---|---|---|
| 两端各写一套，不共享代码 | 系统能力差异太大 | 同一个功能要写两遍 |
| 数据存本地 JSON，不用数据库 | 简单、可读、易备份、易迁移 | 数据量大时性能会下降（目前规模没问题） |
| AI 默认关闭 | 隐私优先 | 用户要手动配置才能用 |
| 不自动同步 | 避免冲突和数据丢失 | 换电脑要手动备份迁移 |
| 关闭窗口不退出（托盘/菜单栏常驻） | 番茄钟要一直跑 | 新用户容易以为"没启动" |
| ad-hoc 签名 | 没有付费开发者账号 | 首次打开可能被系统拦 |
| CI 不测真实系统交互 | 图形环境、权限、真实 AI 都难自动化 | 必须人工验收 |

### 15.2 已知限制

**Windows 端**

- 不支持 Chrome 守护（无 AppleScript 等价物）。
- 不支持系统专注模式联动（issue #63 在评估 Windows Focus API）。
- 不支持 Liquid Glass 玻璃效果。
- 托盘菜单、全局热键、安装卸载流程需要实机验证。

**macOS 端**

- 需要 macOS 14+，编译需要较新的 SDK。
- 首次运行需要授予辅助功能、Apple Events、屏幕录制等权限。
- 未公证，首次打开可能被 Gatekeeper 拦。

**两端共同**

- 没有云同步、账号系统、自动更新器。
- 定时任务（每日回顾）需要应用保持运行。
- AI 会出错，尤其是图片文字识别和材料不足时。

### 15.3 如果你是新手，建议的阅读顺序

1. 先看 `README.md` 的功能介绍，知道这东西能干什么。
2. 再看本文第 2、4 节，建立"目录在哪、东西在哪"的地图。
3. 然后看第 7 节（数据模型）——理解数据就理解了一半。
4. 挑一个你感兴趣的功能，按第 10 节的索引去看对应源码。
5. 想改代码，先按第 13.4 节走一遍流程，跑通测试再说。
