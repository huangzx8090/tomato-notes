# 维护者发布流程

## 工作流

| 文件 | 触发 | 结果 |
| --- | --- | --- |
| `.github/workflows/ci.yml` | 指向 main / develop 的 PR、main / develop 推送、手动运行 | macOS 与 Windows 测试、编译；打包输入（含 `Windows/`）变更或手动勾选 `package` 时生成双架构 macOS 包与 Windows x64 安装包，暂存 7 天 |
| `.github/workflows/release.yml` | 推送 vX.Y.Z 标签，或手动输入已存在标签 | 检查标签、测试、并行打包 macOS / Windows，完整上传后发布同一 GitHub Release |

CI / 发布构建采用 `macos-15` 和 `/Applications/Xcode_26.3.app`，因为代码编译需要 macOS 26 SDK。运行最低版本仍设为 macOS 14。工具链选择参考 [GitHub 官方镜像清单](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-Readme.md)，以后镜像移除该 Xcode 时需在变更分支更新并重新跑 CI。

普通应用源码和文档变更不制作 ZIP / DMG。`Packaging/`、`Scripts/`、`.github/workflows/`、`Package.swift` 或 `Package.resolved` 变更时，测试与编译成功后额外运行 **双架构安装包验证**。PR 比较共同祖先到来源提交的差异；推送比较整个 before → after 范围。无法可靠比较提交时保守执行完整打包。

临时需要预览安装包时，在 Actions → **macOS CI** → **Run workflow** 选择分支并勾选 `package`；不勾选时只运行测试与编译。预览包位于该次运行的 `TomatoNotes-macOS-universal` artifact，不创建或更新 Release。手动运行入口来自默认分支，新输入需随工作流合入 main 后才会显示，参见 [GitHub 手动运行规则](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onworkflow_dispatch)。

两个架构分别编译，立即复制各自二进制再用 `lipo` 合并，兼容 SwiftPM 复用输出路径的工具链。每个安装包内只有正式应用、图标与签名资源；DMG 另附 Applications 链接和安装说明。不会收集 `build/` 内个人资料、验证目录或钥匙串。

## 发布一个新版本

1. 从最新 origin/develop 建立 `release/vX.Y.Z` 分支，遵守 [开发约定](../CONTRIBUTING.md)。
2. 修改 `Packaging/Info.plist` 中 `CFBundleShortVersionString`（例如 1.3.3）并增加 `CFBundleVersion`，同步修改 `Windows/TomatoNotes/TomatoNotes.csproj` 的 `VersionPrefix`、`AssemblyVersion` 与 `FileVersion`；发布检查会拒绝两端版本不一致。
3. 更新 README 中版本示例、`CHANGELOG.md`，新增 `docs/releases/v1.3.3.md`，核对 `Packaging/安装说明.txt`。
4. 执行 `Scripts/test.sh`、`Scripts/package-release.sh v1.3.3`，检查发布文件；提交中文 commit，推送分支，创建 PR。
5. 先通过功能 PR 合入 develop，再创建 develop → main 的发布 PR；分别等 CI 成功并获得人工合并批准。
6. 在最新主分支创建注释标签并推送；标签应指向已合并的发布提交，不要修改已发布标签。

```bash
git switch main
git pull --ff-only origin main
git tag -a v1.3.3 -m '发布番茄小记 v1.3.3'
git push origin v1.3.3
```

7. 查看“发布 macOS 与 Windows 应用”工作流。成功后同一 Release 应有 macOS DMG / ZIP、Windows x64 安装 EXE、`SHA256SUMS.txt`、`INSTALL.txt` 和 `WINDOWS-INSTALL.txt`，且版本、标签、提交与清单一致。两个平台都构建成功才会公开；Windows 失败时不会先发布只有 macOS 的下载页。

首次发布使用 `v1.3.1`（build 8），不为没有实际发布包的历史版本补造标签。

## 发布前的自动检查

- 标签格式是 `vX.Y.Z`，与 Info.plist 精确相同。
- 标签指向检出的提交，且已属于 `origin/main` 历史。
- 对应 `docs/releases/vX.Y.Z.md` 存在。
- macOS 规则测试及 Windows 核心 / 模拟 HTTP 测试通过。
- Windows 使用 .NET 8 自包含 `win-x64` 发布，Inno Setup 生成中文安装 EXE；版本与 Info.plist 一致，PE32+ / x86-64 与 SHA-256 通过检查。
- 应用含 arm64 / x86_64，ad-hoc 签名严格验证通过。
- ZIP 解包后保留可执行权限、签名和双架构。
- DMG 可通过 `hdiutil verify`，全部附件可通过 SHA-256，下载附件名只用 ASCII，避免 GitHub 重命名。
- 发布先创建 draft，再上传全部四个附件，核对服务器实际附件名，最后转为正式 Release；未完整上传不提前公开下载页。

CI 不执行真实 Chrome 关闭、截图、系统授权或图形快捷键集成检查，也不调用真实 DeepSeek。Windows 构建不覆盖托盘、通知、安装/卸载、系统快捷键与真实界面；这些必须在 Windows 实机单独验收，不能把 CI 绿色视为所有系统行为通过。

## 权限与凭据

- 普通检查与构建 job 仅 `contents: read`；检出不保留 Git 凭据。
- 仅发布附件的 job 使用 `contents: write`；不运行仓库构建脚本，避免构建代码持有写令牌。
- 使用仓库自动提供的 `GITHUB_TOKEN`，不需要个人 PAT 或 DeepSeek Key secrets。
- Actions 固定到完整 commit SHA，注释标注主版本。升级时核对官方仓库并在 PR 上验证。
- 推送标签须由有权限的维护者执行；不要指望用工作流自身的 `GITHUB_TOKEN` 再推标签触发另一个工作流，参见 [GitHub 的事件触发限制](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)。
- 私有仓库的 Release 仍为私有，仅有仓库权限的人能下载；发版不自动公开仓库。

## 构建产物与校验

```text
build/releases/v1.3.2/
  TomatoNotes-v1.3.2-macOS-universal.dmg
  TomatoNotes-v1.3.2-macOS-universal.zip
  SHA256SUMS.txt
  INSTALL.txt
```

应用内部版本来自 `Packaging/Info.plist`，不由 tag 临时覆盖。打包脚本在本机和 Actions 使用同一套逻辑，不会在发布期间修改应用资料库。

## 失败后重跑

- 构建 / 测试失败：先定位日志，通过新分支修复。已经发布的标签不强行移动；若应用内容改变，应使用新版本。
- 上传中断且 Release 仍为 draft：使用同一工作流的 Re-run，或在 Actions 手动输入该已有 tag；草稿附件可以重新完整上传。
- 已经正式发布：流程拒绝覆盖。要修复安装包内容或源码，应增加版本并发新 tag；单独编辑文字说明可由维护者操作。
- 不用删除已有正式 Release 或移动标签来掩盖失败。

## 当前签名与后续改进

当前仅做 ad-hoc 签名，无 Apple Developer ID 和公证。这可以校验文件在打包过程中未损坏，但不能证明发行身份，首次下载可能被 Gatekeeper 拦截，钥匙串或隐私授权也可能在升级后重新询问。

如果以后具备 Apple 开发者分发凭据，可在独立变更中加入 Developer ID、Hardened Runtime、正确的 Apple Events entitlement、公证与 stapling；届时需要额外的凭据管理和真实启动 / Chrome 授权验收。当前工作流没有空置的证书配置，不会伪装为已公证版本。

Windows 当前也没有 Authenticode 商业签名。自包含运行库只消除 .NET 安装依赖，不代表 SmartScreen 信任。若以后配置签名，应使用受保护的签名凭据，并验证安装器与卸载流程。
