# 双端协作维护

番茄小记使用一个仓库维护两个原生客户端：macOS（Swift / SwiftUI）与 Windows（C# / WPF）。两端共享资料契约、产品版本和发布流程，各自维护业务实现与 UI。

## 目录与维护责任

| 路径 | 主要维护人 | 内容 |
| --- | --- | --- |
| `apps/macos/` | macOS 维护者 @huangzx8090 | Swift 应用、规则、系统接口、测试与打包 |
| `apps/windows/` | Windows 共同维护者 @blakceyes、@yhy854 | WPF 应用、规则、系统接口、测试与安装器 |
| `Compatibility/` | 双方共同评审 | 数据契约、兼容样例与迁移约定 |
| `VERSION`、`Scripts/check-versions.py`、`Scripts/validate-release.sh` | 双方共同评审 | 产品版本、两端一致性与标签校验 |
| `.github/`、仓库协作脚本 | 双方共同评审 | CI、发布、分支与协作入口 |
| `README.md`、`CHANGELOG.md`、`docs/releases/` | 双方共同维护 | 用户文档与发布记录 |
| `AGENTS.md`、`CONTRIBUTING.md`、本文 | 双方共同维护 | 人工与 AI 协作规则 |

各自通常在独立克隆中开发。根目录的 `Scripts/test.sh`、`build-app.sh`、`package-release.sh`、`check-integration.sh` 和 `package-windows.ps1` 保留为兼容转发入口，实际实现位于对应平台的 `Scripts/`。构建输出继续写入仓库根目录 `build/`，SwiftPM 缓存在 `apps/macos/.build/`。

“主要维护人”不是排他权限；跨端修改需具备任务授权，涉及另一端核心行为、数据契约或发布流程时，需要该端维护者评审。

开分支和 PR 操作统一见 [CONTRIBUTING](../CONTRIBUTING.md)，发布与回同步见[发布流程](发布流程.md#发布一个新版本)。

## 跨端跟进

每次交付一端的功能、修复或改进前，AI 必须检查另一端的当前代码和已有 issue，并作出以下判断。此规则双向适用：Windows → macOS 与 macOS → Windows。

| 本次改动 | 是否自动提另一端跟进 issue |
| --- | --- |
| 新增另一端缺少、且同样适用的用户功能 | 是，说明目标端需要补齐的能力 |
| 修复计时、日期、数据保存、统计、AI 协议等共同逻辑，另一端存在同类问题或有代码依据表明需要排查 | 是，提供触发条件、根因与可借鉴方案 |
| 优化操作流程、性能、数据保护等，另一端能直接受益 | 是，描述收益与目标端适用依据 |
| 修复 Windows 专属 Win32 / WPF / DPAPI / 安装器问题，macOS 没有同类问题 | 否，说明平台特有原因 |
| 修复 macOS 专属 AppKit / AppleScript / Keychain / 签名问题，Windows 没有同类问题 | 否，说明平台特有原因 |
| 另一端已实现、已有跟进事项，或本次已同步完成两端修改 | 不重复创建；必要时补充已有 issue |
| 纯目录整理、内部等价重构、格式化或文档改动，没有待迁移的行为变化 | 否 |

不能只根据文件所在平台或提交类型判断。比如托盘相关代码中的“重复触发保存”也可能来自共同业务逻辑；须检查目标端是否有同类调用。尚未证实的目标端缺陷标记为“待确认”，不能写成已复现。目标端不支持且没有适用场景的系统能力不机械要求移植。

### 执行顺序：优先使用 gh

1. 确定来源端、目标端和具体行为，检查目标端对应代码。功能已存在时不制造重复需求。
2. 优先使用 `gh issue list --state all --search ...` 查重，搜索目标端名称、功能词、来源 PR 等；用 `gh issue view` 阅读候选事项。不能只搜索 open issue，已关闭事项也可能说明功能已完成或已明确不采纳。
3. 来源实现可评审并已创建 PR 后，使用 `gh issue create --body-file` 创建跟进事项；不必等待合并，正文明确“来源 PR 待合入”。已有对应事项则通过 `gh issue comment --body-file` 补充来源与差异，不反复发送相同说明。已关闭但需要重新评估时补充新依据，由维护者决定是否重新打开。
4. 在来源 PR 的“跨端跟进”和最终交付中记录 issue 链接；无需提 issue 时写明具体原因。多个无关功能分开跟进，同一功能的相关改动合并说明。
5. 目标端后续自行建分支实现，验证后由对应 PR 关联并关闭事项；来源 PR 不使用 `Closes` / `Fixes` 提前关闭目标端事项。

已获本仓库此类协作授权时，AI 满足上述条件后直接执行，不把正常提 issue 再变成一次确认。该授权限于本仓库的跨端跟进，不扩展为自动实现另一端或自动合并。

`gh` 不可用或权限不足时，可改用已连接且具备权限的 GitHub 工具。仍无法完成时，保留完整标题与正文，在交付中明确“未创建 / 未补充”、失败原因和待办；不能声称已经通知。仅使用已存在的合适 label，不填猜测的 assignee，也不把日志、密钥或个人资料贴进 issue。

### Windows 默认同时委派两人

- macOS 跟进 issue 指派 @huangzx8090；Windows 跟进 issue 在同一个事项上同时指派 @blakceyes（khalil）和 @yhy854。不轮流分配，不只选其中一人，也不为同一需求给每人各开一个重复 issue。
- 操作前优先用 `gh api repos/huangzx8090/tomato-notes/assignees/<用户名>` 检查两位成员是否可被指派。仓库邀请尚未接受、账号或权限发生变化时，不能只凭维护者名单推断实际指派可用。
- 两人均可被指派时，创建 issue 带两个 `--assignee`；补充已有 issue 时，只用 `gh issue edit --add-assignee` 添加缺少的人员，保留其他已有 assignee。
- 有成员暂不可指派时，先创建 / 补充事项并指派可用成员，交付时写明尚未成功指派的人及原因。成员恢复可用后，对该事项补齐缺少的指派；不得声称仅 @ 提及或写入 CODEOWNERS 已完成 issue 委派。
- 操作后通过 `gh issue view <编号> --json assignees` 核对实际结果。创建事项和设置 assignee 是两项结果，分别如实报告。

### issue 内容

标题使用 `[跨端跟进][macOS] <待补能力或待排查问题>` 或 `[跨端跟进][Windows] ...`。正文至少包含：

- 来源平台、来源 PR / commit，以及待合入 / 已合入状态。
- 本次新增行为，或 bug 的触发条件、根因与修复方式。
- 目标端当前情况、适用依据，以及待确认之处。
- 建议迁移方案；需区分共同业务规则和源端特有 API。
- 可操作的验收条件、兼容或迁移要求，以及已执行与未执行的验证。

可使用 `.github/ISSUE_TEMPLATE/cross-platform-follow-up.yml`。命令示例（从仓库根目录执行）：

```bash
gh issue list --repo huangzx8090/tomato-notes --state all --search 'macOS 待办批量结转' --limit 50
gh issue view <已有事项编号> --repo huangzx8090/tomato-notes --comments

# 先将完整 Markdown 正文写入临时文件，再提交，保留真实换行。
gh issue create --repo huangzx8090/tomato-notes --title '[跨端跟进][macOS] 支持待办批量结转' --assignee huangzx8090 --body-file /绝对路径/issue-body.md

# Windows：先分别核验两人；以下双人指派命令仅在两人均可被指派时执行。
gh api --silent repos/huangzx8090/tomato-notes/assignees/blakceyes
gh api --silent repos/huangzx8090/tomato-notes/assignees/yhy854
gh issue create --repo huangzx8090/tomato-notes --title '[跨端跟进][Windows] 支持待办批量结转' --assignee blakceyes --assignee yhy854 --body-file /绝对路径/issue-body.md

# 已有事项时补充，不重复创建。
gh issue comment <已有事项编号> --repo huangzx8090/tomato-notes --body-file /绝对路径/issue-update.md
gh issue edit <已有Windows事项编号> --repo huangzx8090/tomato-notes --add-assignee blakceyes --add-assignee yhy854
gh issue view <事项编号> --repo huangzx8090/tomato-notes --json assignees
```

## 代码所有者

`.github/CODEOWNERS` 登记 macOS 维护者 @huangzx8090 和 Windows 共同维护者 @blakceyes（显示名 khalil）、@yhy854。平台目录由对应维护者负责，数据契约、版本与发布流程列出全部维护者。新成员须接受仓库邀请并获得 write 权限后，才能作为有效代码所有者；预先登记账号不代表其权限已经就绪。后续人员变化时同步更新此文件与本文。

CODEOWNERS 表达路径维护关系；自动请求或强制评审的可用性取决于仓库权限、计划与分支保护配置，按[权限维护约定](../CONTRIBUTING.md#分支与权限维护)核验实际状态。

## 共享改动与交接

- 数据格式、未知字段保留、版本迁移和备份要求统一见[资料契约](../Compatibility/README.md)。先对齐字段、行为与迁移方案；跟进 issue 不能替代本次必需的兼容修复。
- 两端版本与同一 Release 的一致性要求统一见[发布流程](发布流程.md)，涉及这些共享流程时需要双方评审。
- 用户可见变化更新相应说明；PR 明确影响平台、实际验证与实机未验证范围。目标端后续按跟进 issue 自行安排实现。
